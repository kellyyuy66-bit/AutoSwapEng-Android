# 翻转外语自动打卡 —— 问题诊断与解决方案

> 面向对象：AutoSwapEng-Android v0.2.1（`com.autoswapeng.app`）  
> 分析依据：源码 + 实机运行日志 `log_20261010_170237.txt` + 运行期截图 `.local/shots/*.png` + 打卡流程视频封面  
> 实机环境：1280×2772 / DPI 520（竖屏）

---

## 一、结论（先看这里）

**这个 app 目前不是一个「自动打卡」程序，而是一个「手动触发单个题型、靠 OCR 硬猜」的半成品原型。**

它"能跑起来"，是因为无障碍服务、悬浮窗、MediaProjection 三条链路都接上了；  
它"完不成"，是因为**真正决定成败的四个环节全部不可用**：

| # | 致命问题         | 一句话                                      | 严重度   |
| - | ------------ | ---------------------------------------- | ----- |
| 1 | 截图成功率极低      | 284 次截图失败，OCR 拿不到图                       | ★★★★★ |
| 2 | 悬浮窗/自身界面污染截图 | OCR 把自己的按钮文字当成题目                         | ★★★★☆ |
| 3 | 选项模型错误       | 代码只认 4 个选项，真题是 5 个（含"我不确定"）              | ★★★★☆ |
| 4 | 缺少打卡导航状态机    | `onAccessibilityEvent` 是空的，不会"进任务→答题→返回" | ★★★★★ |

加上两个结构性问题（5、6），共同导致：**循环 80 次、耗时 5 分半，只学到 2 个残缺单词、答了 3 题，然后卡在"必须要作答哦~"弹窗上无限循环。**

## 三、根因逐条分析

### 根因 1：截图成功率极低（核心）

**证据**：284 次失败 vs 偶尔成功。

**位置**：`ScreenCaptureHelper.captureScreen()`

**技术原因**：MediaProjection 的 VirtualDisplay 是**镜像**，只有屏幕内容发生变化时才会产生新帧。而现有代码的逻辑是：

```kotlin
// 1. 先把队列里所有旧帧清空
while (oldImage != null) { oldImage.close(); oldImage = acquireLatestImage() }
// 2. 睡 200ms
Thread.sleep(200)
// 3. 再尝试 5 次 acquire
for (retry in 1..5) { image = acquireLatestImage(); if (image != null) break; Thread.sleep(150) }
if (image == null) return null      // ← 屏幕静止就必然返回 null
```

清空队列后，如果画面是静止的（比如一个弹窗停在那里、或同一页面没重绘），**<u>不会有新帧进来</u>**<u>，`acquireLatestImage()` 只能返回 null。所以现象是"点击/滑动后偶尔成功，静止时必然失败"</u>。

**影响**：OCR 拿不到图 → 单词/释义/选项全部读空 → 学习记忆库为空 → 答题无依据 → 全部走 `QUIZ_FALLBACK` 瞎点。

**附加问题**：每次截图最长耗时 ~~950ms（200ms + 5×150ms），一个循环要截图 2~~3 次 × 80 循环，界面卡顿且极慢。

---

### 根因 2：悬浮窗 / 自身界面污染截图

**证据**：OCR 结果里混进了 app 自己的控件文字：

```
17:04:44.494 [quiz-options] OCR: 'A. n.ê5E ... E. l OCR A. n.持枪歹徒 ... 公开始拼写 口停止学习 0开始听力 Q节点 关闭悬浮窗'
17:04:44.494                                                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                                                 全是悬浮窗上的按钮文字
```

甚至把 app 自己的日志页整屏都截进去了（17:05:24、17:07:54、17:08:00 的 OCR 结果里出现 `500条 D:356 I:39 W:105 E:0`、`于日志`、`app-debug.apk 99.7 MB`）。

**原因**：悬浮窗是 `TYPE_APPLICATION_OVERLAY`，会被 MediaProjection 一起捕获；而且没有做"当前是否在微信前台"的校验。

**影响**：OCR 结果被污染 → `extractChineseOptions` / `extractEnglishOptions` 解析出错误选项 → `WordMatcher` 匹配错误 → 选错答案。

---

### 根因 3：选项模型错误（4 个 vs 5 个）

**证据**：实机截图与 OCR 都显示题目是 **5 个选项 A–E**，其中 E 固定是"我不确定"：

```
17:07:50.484 [quiz-options] OCR: 'downturn [...] A. conj.然而;鉴于;反之 B. ad.有点儿;有几分 C. n.衰退,低迷时期 D. n.药草;草本 E. 我不确定'
```

而 `PrototypeSelectionHandler` 与 `MiniProgramRegions.Selection` **只定义了 4 个**：

```kotlin
val OPTION_A = NormalizedPoint(0.5060f, 0.5284f)
val OPTION_B = NormalizedPoint(0.5060f, 0.5938f)
val OPTION_C = NormalizedPoint(0.5060f, 0.6633f)
val OPTION_D = NormalizedPoint(0.5060f, 0.7353f)   // 没有 OPTION_E
```

**影响**：

- 若正确答案恰好是 E，永远选不中；
- `extractChineseOptions` 用正则 `[ABCD]\.` 切片，遇到 5 选项会把 E 的内容漏掉或错位；
- 更糟：这些归一化坐标是从**别的设备/截图**量出来的，与实机 1280×2772 的选项实际位置（y 约 0.40~0.87）明显不符，**点到的位置根本不是选项**。

---

### 根因 4：没有打卡导航状态机（最本质）

**证据**：`AppAccessibilityService.onAccessibilityEvent()` 内容只有一句 `TODO`：

```kotlin
override fun onAccessibilityEvent(event: AccessibilityEvent?) {
    if (!isServiceEnabled) return
    val packageName = event?.packageName?.toString() ?: return
    if (packageName !in TargetApps.PACKAGE_NAMES) return
    if (event?.eventType == AccessibilityEvent.TYPE_WINDOW_STATE_CHANGED) { ...日志... }
    // TODO: 在这里实现自动处理逻辑
}
```

所有能力只能靠悬浮窗上三个按钮**手动**触发：`开始拼写` / `开始学习` / `开始听力`。

**但你的打卡需求是**（见视频封面：`今日任务` 页 → `单词任务` 页 → `开始` → 答题 → 返回）：

> "打卡流程需要每个点进去然后完成" —— 即：识别今日任务列表 → 依次点进「测试 / 单词 / 听力 / …」→ 完成内部所有题 → 返回列表 → 下一个 → 直到 6/6。

**这部分代码完全不存在**：没有任务列表识别、没有"进入任务"、没有"任务内部完成判定"、没有"返回上级"。

---

### 根因 5：坐标区域与真机不符

`MiniProgramRegions` 注释写的是"基于 1080×2400 屏幕已归一化"，但实测设备是 **1280×2772**，且多组点位明显落在错误位置（例：`NEXT_TAP = (0.5060, 0.3006)` 实际落在标题栏）。虽然归一化理论上可跨设备，但**这些数值本身是从另一台设备的截图上量的**，不是本机标定值。

---

### 根因 6：记忆库不持久化 + 逻辑强依赖"先学后测"

`WordMatcher.memory` 是纯内存 `LinkedHashMap`。小程序每轮任务会重新进入，一旦服务重启、任务切换或中途停止，记忆库即清空；此时"中→英"题（如截图里的 `disconnect`）需要**反查**之前学过的释义才能作答，记忆库空了就永远返回选项 0。

---

## 四、解决方案

整体思路：**先把"看"和"点"两个基础能力做可靠，再补打卡主流程。** 分三阶段，每阶段都可独立验证。

### 阶段 0：修基础设施（最高优先级，1~2 天）

#### 0.1 截图稳定化 —— 用「常驻缓存帧」替代「同步拉取」

把 `ScreenCaptureHelper` 改成监听式：注册 `OnImageAvailableListener`，始终保存最新一帧的 Bitmap；`captureScreen()` 直接返回缓存帧。**不再清空队列、不再依赖"屏幕变化"。**

```kotlin
// ScreenCaptureHelper.kt
private var latestBitmap: Bitmap? = null
private val bitmapLock = Any()

// initMediaProjection 里创建 ImageReader 后注册监听
imageReader = ImageReader.newInstance(rawWidth, rawHeight, PixelFormat.RGBA_8888, 3)
imageReader?.setOnImageAvailableListener({ reader ->
    val image = reader.acquireLatestImage() ?: return@setOnImageAvailableListener
    try {
        val bmp = imageToBitmap(image)   // 抽出的原 convert 逻辑
        synchronized(bitmapLock) {
            latestBitmap?.recycle()
            latestBitmap = bmp
        }
    } finally { image.close() }
}, handler)

// 截图：优先用缓存，最多等 300ms 拿第一帧
private fun captureScreen(): Bitmap? {
    synchronized(bitmapLock) { latestBitmap?.let { return it.copy(Bitmap.Config.ARGB_8888, false) } }
    // 冷启动兜底：注册一个一次性回调等待首帧，超时 300ms
    return awaitFirstFrame(300)
}
```

要点：

- `maxImages` 提到 3，避免丢帧；
- 首次没有缓存时只等一次（超时即返回 null），**不要**再写 `while` 清空队列；
- 保留 `isInitialized()` 判定不变。

**验收**：连续截图 50 次，成功率 ≥ 95%（现状 <5%）。

#### 0.2 截图时隐藏自身悬浮窗 —— 或用 FLAG_SECURE

给悬浮窗加 `FLAG_SECURE`，它就不会出现在 MediaProjection 里（最省事）：

```kotlin
// FloatingWindowService.createFloatingWindow()
val params = WindowManager.LayoutParams(...).apply {
    flags = flags or WindowManager.LayoutParams.FLAG_NOT_FOCUSABLE
                  or WindowManager.LayoutParams.FLAG_SECURE   // ← 关键：排除自身截图
}
```

若担心某些 ROM 不生效，再加一层保险：截图前把悬浮窗 `alpha = 0f` 并 `updateViewLayout`，截图后恢复。

#### 0.3 加"目标应用前台校验"

在每个流程开始截图前，先判断当前前台应用：

```kotlin
// 用无障碍事件里缓存的 currentPackage，或 UsageStats
if (currentForegroundPackage != "com.tencent.mm") {
    LogManager.w(TAG, "当前不在微信前台，跳过本次截图")
    return ""
}
```

**验收**：OCR 结果里不再出现"开始拼写/停止学习/关闭悬浮窗"等自身控件文字。

#### 0.4 统一坐标系标定

- 关掉"基于 1080×2400"的旧注释，改为**以本机实机截图重新标定**；
- 建议加一个隐藏的"标定模式"按钮：在目标页显示十字准星，点击后记录该点归一化坐标，导出 JSON，直接覆盖 `MiniProgramRegions`。

**验收**：点击"选项 A/B/C/D"能与 UI 上四个选项框的中心误差 < 20px。

#### 1.1 支持 5 个选项（A–E）+ "我不确定"兜底

val OPTION_A = NormalizedPoint(0.5060f, 0.5284f)

val OPTION_C = NormalizedPoint(0.5060f, 0.6633f)

val OPTION_E = NormalizedPoint(0.5060f, 0.8070f)   // ← 新增（数值需按 0.4 重新标定）

val OPTIONS = listOf(OPTION_A, OPTION_B, OPTION_C, OPTION_D, OPTION_E)
```

```kotlin
// 选项解析：支持 A~E，且把"我不确定"单独标记，不参与匹配
private val OPTION_LABELS = listOf('A','B','C','D','E')

private fun extractChineseOptions(raw: String): List<String> {
    val pattern = Regex("[ABCDE][\\.、](.*?)(?=[ABCDE][\\.、]|$)")
    return pattern.findAll(raw).map { it.value.substring(2).trim() }
        .filter { containsChinese(it) }.toList()
        // 保留 E（"我不确定"）在列表中，但匹配时降权
}
```

匹配逻辑：**"我不确定"永远不作为正确答案**（它是一个错误选项），若 `WordMatcher` 最高分落在 E，则改选次高分。

```kotlin
val idx = matcher.match(word, options)
val finalIdx = if (options.getOrNull(idx)?.contains("不确定") == true) {
    // 取次优
    matcher.rank(word, options).first { !options[it].contains("不确定") }
} else idx
```

#### 1.2 处理"必须要作答哦~"弹窗

截图 `fullscreen_170907_44.png` 明确显示：未作答时弹出模态框「必须要作答哦~」，下方绿色「确认」按钮。现有代码没有任何处理，导致点击全部打在弹窗遮罩上。

```kotlin
// 每次点击前先"清障"
private suspend fun dismissBlockingDialogIfAny(): Boolean {
    val t = screenCapture.captureAndRecognize(Selection.DIALOG_TIP_AREA, "dialog").trim()
    if (t.contains("必须") || t.contains("作答")) {
        val (x, y) = Selection.DIALOG_CONFIRM.toPixelPoint(sw, sh)
        tap(x, y); delay(400)
        return true
    }
    return false
}
```

并在主循环开头调用它。`DIALOG_TIP_AREA` / `DIALOG_CONFIRM` 需按 0.4 标定（弹窗提示约在 y=0.44，确认按钮约在 y=0.62）。

```kotlin

**验收**：学完一个卡包后杀掉服务重启，再次进入任务仍能答对"中→英"题。

### 阶段 2：补打卡导航状态机（3~5 天，真正实现"自动打卡"）

新增一个顶层调度器 `TaskListNavigator`，实现"从今日任务页到 6/6"的完整闭环：

```
状态：任务列表页
  ├─ 截图识别 8 个任务卡片的标题 + 完成度（"已完成 x/y"）
  ├─ 找到第一个"未完成"的卡片
  ├─ tap 进入 → 状态：任务内部
任务内部（复用已有 handler）
  ├─ 单词/测试 → PrototypeSelectionHandler
  ├─ 听力       → ListeningHandler
  ├─ 其他       → 先记录"暂不支持"，按返回退出
  ├─ 完成判定：OCR 底部出现"完成/返回/继续"或完成度变化
  └─ 按返回键（performGlobalAction(GLOBAL_ACTION_BACK)）回到列表
回到 状态：任务列表页 → 循环，直到所有卡片显示"已完成"或达到 6/6
```

关键点：

- **返回上级**用无障碍的 `performGlobalAction(AccessibilityService.GLOBAL_ACTION_BACK)`，比点左上角箭头稳；
- 任务完成判定不要靠"数题数"，靠**页面文案变化**（如出现"今日进度 100%"或"已完成"徽标）；
- 每完成一个任务回到列表页重新识别，避免状态漂移；
- 用 `onAccessibilityEvent` 监听 `TYPE_WINDOW_STATE_CHANGED`，实现"页面一变就推进状态机"，而不是死循环轮询。

**验收**：从「今日任务」页启动一次，无人干预跑完 → 今日完成率 100%（6/6）。

## 五、强烈建议：改成「无障碍节点优先 + OCR 兜底」的混合方案

现状是**纯 OCR**（截图→识别文字→按坐标点击），这条路线有三个天然缺陷：慢（每步 ~1s）、脆（分辨率/字体/弹窗一变就崩）、脏（会读到悬浮窗自己）。

而这个目标是**微信小程序**，其 WebView 里的文字**很多时候能被无障碍节点树读到**（小程序渲染层会把文本节点暴露出去）。建议：

1. **优先用 `AccessibilityNodeInfo` 遍历取文本 + `performAction(ACTION_CLICK)` 点击**——精准、快、不受分辨率影响；
2. **只有节点树读不到时**（Canvas 绘制、图片文字）才回退到 OCR；
3. 项目里已经有 `NodeDebugger.detectNodes()` 和悬浮窗的"🔍 节点"按钮——**先点它导出当前页面节点 JSON**，就能立刻确认小程序是否暴露了可点的文本节点。

> 这一步的收益最大：如果节点能读到，根因 1/2/3/5 会**同时消失**，代码量还能显著减少。
